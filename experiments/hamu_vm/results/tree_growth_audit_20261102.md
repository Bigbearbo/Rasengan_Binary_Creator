# 倉鼠記憶樹成長性檢查與保護（2026-11-02）

本輪研究立場：**成長正確性優先，不因短題庫的步數表現犧牲未來可擴容性。** 此立場來自使用者原話：「也不用太在意快，一時快可能變大之後反而慢了，好的成長型設計優先。繼續」。

## 實作修改（與未完成事項明確區分）

F（已改程式）：

1. `src/hamu_vm_core.hpp`：新增 `tree_lookup_rows_examined` 原生掃描計數，TREE_FIND/TREE_ADD（含 register 版本）每掃描一行計一次；**這是診斷計數，不列入 `executed_steps` / HP**。因原 ISA 將一整次 TREE_FIND 視為一條 VM 指令，先前 VM 步數漏看原生逐列尋找的成長成本。
2. `src/hamu_vm_core.hpp`：`copy_hamu` 現在核對 `tree_start` 與 `tree_capacity`；不同樹布局不能直接按原位置複製記憶。這是拒絕不相容繼承的保護，**不是自動擴容或資料搬遷**。
3. `src/tree_compact_reference.hpp`：舊的五位 guest 暫存用 `base-5..base-1`；在 `tree_start=300,capacity=31,base=672` 時是 667..671，剛好與原 TREE_ACTION 區（579..671）末端重疊。現改用 `base+31*12..+4`（1044..1048），置於整段緊湊 payload 後面；加上程式區前端邊界檢查。**不移動既有 payload**，避免破壞舊記憶位址。已發生過的舊暫存覆寫不能由程式猜回原內容。
4. 新增 `tests/test_tree_compact_growth.cpp`，驗證 cap=1/2/4/8/16/24/31 的滿額路徑、最後節點資料位置、試錯、確認、同布局繼承、改布局拒絕及混用 TREE_ACTION 資料的暫存隔離。
5. 新增 `prototypes/segmented_tree_growth_ref.hpp` 與 `tests/test_segmented_tree_growth_ref.cpp`，**獨立的宿主參照原型，不是 VM 客體具備的新樹指令**。概念以每段 31 個 slot、穩定跨段 handle、3-bit 路徑、增量配置、容量不足時事前拒絕，驗證 >31 節點的資料擴展契約。其 `std::unordered_map`、64-bit parent ID 和 C++ 物件成本與現有 9+12 位布局不同，不能作為記憶體或性能改善證據。
6. 新增 Makefile 測試目標；舊題目、學習規則、ISA 和實體題庫仍未改。

## 本輪量化實測（T）

使用 `g++ -std=c++17 -O1 -g -fsanitize=address,undefined -fno-omit-frame-pointer` 編譯重跑核心相關測試，測試 log 見 `results/tree_growth_regression_20261102.log`。

以上指標是**操作行為與記憶位元的計數**，不是 CPU wall-clock 速度。隨容量增大，內部逐列搜尋增加但 VM 指令步數變化小，說明以步數判斷長期成本會失真。預留 21 位／節點未含暫存、程式、索引、宿主物件及其他 VM 記憶。

同題目、同回饋 15 次試答重播：舊答案節點方案 2,326 VM 步、41 呼叫、13 節點；修正暫存位置後的緊湊方案 1,982 VM 步、52 呼叫、2 節點。前一輪未修正暫存隔離時緊湊曾測得 1,774 步，**不可拿舊速度覆蓋新的安全版本**。兩方案 VM 內部掃描與宿主索引、程式長度未做完整生命週期公平計費。

四倉鼠、二題、11 輪受控世界：216 次 VM 呼叫、9,809 VM 步、峰值 92 步、8 個題目節點；最後四隻全答對、資源總額 3,600。和前一輪 8,689 步（使用原重疊暫存位置）的結果相比，多 1,120 步；學習輪次和資源序列不變。這次的代價源於避免內存覆蓋，不應強行微優化回錯誤布局。

宿主分段樹原型在 3000 個不同鍵上建立 3,429 個節點、111 段；測得第一個跨過 31 節點的題目序號為 24；早期的穩定 handle、錯誤排除、正解、C++ 複製和容量不足時無部分插入均通過。**此結果只證明該 C++ 參照模型的功能，不是客體 VM 的跨段學習成果，也沒測實際內存開銷或長期 HP**。

`test_vm`、`test_tree_vm`、`test_stable_work`、`test_tree_error_trial`、`test_tree_compact_world`、`test_tree_compact_reference`、`test_tree_compact_optimized_cost`、`test_tree_compact_growth`、`test_segmented_tree_growth_ref`：九個可執行檔均 PASS。其中 `test_vm` 包含 6,000 個隨機 VM 客體。此輪尚未執行跨 31 節點的真實 VM、完整 652 題、自主病毒市場或嚴格 Zero 世界。

## 設計判斷及下一步（A/H，不冒充實作）

[更新] 用「容量邊界、繼承正確性、資料搬遷代價、宿主掃描成本、節點內外可擴容」評估記憶樹成長；短題庫 VM 步數只占其中一項。  
[取代] 優先把 1,774 VM 步進一步壓低，或以小型重播的快慢決定記憶結構。  
[原因] 5-bit ID 上限、3-bit 鍵值、逐列原生掃描不計入 guest 成本、布局重疊與跨世代布局風險；皆為直接程式檢查與部分本輪實測。  
[狀態] 信心高：已列出的程式限制、隔離修正、測試結果；信心中：下一代分段樹的選型，需要客體 ISA 設計與世界級測試。

建議的長期路線：

1. 以**可延展的完整鍵路徑**代表題目，不把題目數直接鎖死在一組 3-bit 即時鍵；舊的八候選錯誤位圖可以是第一種葉片格式，面對更多候選時改用子樹或稀疏試錯紀錄。這是分層編碼，不要求初期就有數學歸納。
2. 讓每段維持 31 個可編址局部節點，跨段採**穩定 handle 與版本資訊**。新增分段不應移動舊 handle；若需要重新布局，必須有明確的交易式搬遷、校驗和失敗回滾，而非在複製時默默解讀另一種布局。
3. 現有宿主原生逐列查詢可先保留作基準，之後比較可維護的索引方式，並記錄索引自身的記憶和維護成本；不要只看 `executed_steps`。是否把宿主查找負擔算進 HP 需專門定義，當前未改資源模型。
4. 真正接入 VM 時需讓客體能表示／保存／操作跨段 handle，實作分段分配、可失敗復原的查詢寫入；目前宿主 C++ 原型**不能替代**這步。
5. 驗收應使用逐步擴大題庫與重複試錯、答案數擴張、記憶接近上限、跨代繼承、世界級長期觀察。只求死記正確和延展，暫不引入語義公式自動壓縮。
