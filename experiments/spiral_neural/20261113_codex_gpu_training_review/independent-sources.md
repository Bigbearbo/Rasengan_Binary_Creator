Driver610.88 is above NVIDIA's documented CUDA13 family minimum580 and CUDA12 family minimum525. This is a nominal compatibility check, not proof that an arbitrary wheel/compiler/PTX combination works; minor compatibility has feature/JIT limitations. Prefer a selected, pinned supported stack and verify it rather than installing whichever CUDA package happens to resolve. [NVIDIA compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/latest/minor-version-compatibility.html), [CUDA13.2 release notes](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-toolkit-release-notes/index.html).

CUDA Graphs reduce repeated host dispatch; they do not fuse all kernels or automatically change the optimizer. [NVIDIA's graph guide](https://docs.nvidia.com/dl-cuda-graph/latest/cuda-graph-basics/introduction.html) explains the small-kernel overhead problem. Importantly, the [2024 NVIDIA launch study](https://developer.nvidia.com/blog/constant-time-launch-for-straight-line-cuda-graphs-and-other-performance-enhancements/) attributes near-constant repeated graph launch to Ampere and explicitly says pre-Ampere remains O(nodes). Its RTX3060/Linux timing numbers must not be presented as GTX1650/Windows predictions.

The semantic risks that matter before accepting any acceleration are:

- **Ordered updates:** targets may be staged together, but token i+1 must use token i's updated weights and Adam state. Replacing several steps with one averaged-gradient minibatch changes the experiment. Independent students may share infrastructure, but clipping, moments and age counters must remain separate.
- **Age and restore:** retain p/m/v, global t, elementwise birth, RNG and counters. PyTorch2.15 [Adam source](https://github.com/pytorch/pytorch/blob/v2.15.0/torch/optim/adam.py) creates a scalar step per parameter tensor, not an elementwise birth array. A custom update is required unless uniform age has actually been established for the supported state scope.
- **Precision and clipping:** preserve FP64 CE, FP32 stored p/m/v, specified cast points, epsilon placement and the global norm/clip1 across that student's four gradient arrays. Matching the mathematical Adam formula alone does not establish identical floating-point behavior. Foreach/fused/autograd implementations must be checked, not assumed equivalent. [Adam API](https://docs.pytorch.org/docs/2.15/generated/torch.optim.Adam.html), [PyTorch numerical accuracy](https://docs.pytorch.org/docs/2.15/notes/numerical_accuracy.html).
- **Implicit promotion:** [Numba floating-point semantics](https://numba.readthedocs.io/en/stable/reference/fpsemantics.html) explicitly warns that mixed integer/float powers can select different precision than NumPy. Write age-power and intermediate precision explicitly. `fastmath=False` still does not promise NumPy's bitwise results; [CUDA fastmath](https://nvidia.github.io/numba-cuda/user/fastmath.html) additionally changes division/sqrt, denormals and contraction when enabled.
- **Captured state:** PyTorch's graph constraints require fixed addresses/shapes, exclude ordinary `.item()` synchronization and do not replay Python work. A Python `t += 1`, Python target index, or CPU-only clipping decision will not advance on replay. Use explicit device mutation or correct pre-replay buffer staging. Capture/compile warmup must not silently add training updates to the initial state. The [`reduce-overhead` mode](https://docs.pytorch.org/docs/2.15/generated/torch.compile.html) has additional applicability/memory constraints; it is not a universal switch.
- **Custom fusion:** finish all gradients and the global norm before mutating weights needed by backprop. An ordinary block barrier does not synchronize different blocks. A persistent all-epoch kernel adds synchronization and Windows display-watchdog/runtime risk; start with bounded steps/graphs, not an unvalidated monolithic kernel. This is a design risk, not a measured failure.

The next authorized benchmark should compare identical public synthetic prefixes/labels and full initial states, including nonzero moments/old t, multiple birth ages and a clipping case. Check CE, predictions and p/m/v/t/birth after each ordered step, with a predefined numerical acceptance rule; strict historical equivalence requires strict state agreement. Otherwise label the backend as a new numerical implementation rather than extending historical exact-replay claims. Test changing targets and counters across graph launches so a repeated constant input cannot masquerade as a valid training loop.

Time context creation, compilation, graph construction and warmup separately from steady-state. Report synchronized device time and end-to-end wall time, including the chosen transfer/checkpoint/metric scope; first-call time and submission-only CPU time are different quantities. [CuPy's performance guide](https://docs.cupy.dev/en/stable/user_guide/performance.html) documents CUDA events, synchronization and startup costs. Framework speed, graph speedup, RawKernel speed, memory peak, long-run numerical agreement and real research runtime are all **unmeasured by this independent review**. No performance factor is accepted from documentation or the rejected external candidate.

**Follow-up: CuPy14.2 cuBLAS capture failure — 2026-11-13, zero new NN operations by reviewer.**

Stream API availability does not establish capture compatibility of matrix multiplication. In the pinned [CuPy v14.2.0 cuBLAS wrapper](https://github.com/cupy/cupy/blob/v14.2.0/cupy_backends/cuda/libs/cublas.pyx), `setStream` checks non-HIP `streamIsCapturing(stream)` and raises `NotImplementedError` before calling `cublasSetStream`. Its comment explains that the wrapper disables this capability pending a robust strategy to test cuBLAS capture conditions. This directly matches the coordinator's preserved attempt02 failure at `h=x@W0`; it is not evidence that GTX1650 or CUDA Graphs are intrinsically unsupported.

The library boundary matters: NVIDIA's [cuBLAS Graphs section](https://docs.nvidia.com/cuda/cublas/index.html#cuda-graphs) allows capture in most situations, with exceptions for host-result synchronization, captured host scalar coefficients and some memory-node/workspace cases. Removing CuPy's guard locally is not a reviewed fix. PyTorch's documented explicit CUDAGraph route remains a possible alternative independent of Triton, but this review has not installed or tested PyTorch.

The proposed `sum(x[:,None] * W, axis=0)` route is source-supported as a way around this particular guard. In [_routines_math.pyx](https://github.com/cupy/cupy/blob/v14.2.0/cupy/_core/_routines_math.pyx), multiplication is an arithmetic ufunc and sum selects CUB, optional cuTENSOR or CuPy's reduction kernel. The fallback in [_reduction.pyx](https://github.com/cupy/cupy/blob/v14.2.0/cupy/_core/_reduction.pyx) launches its own kernel. CuPy's [graph tests](https://github.com/cupy/cupy/blob/v14.2.0/tests/cupy_tests/cuda_tests/test_graph.py) capture elementwise arithmetic; the host branch on `a.sum()` is specifically a synchronization failure example. These sources justify testing a wholly device-resident product/sum chain; they do not prove that every reduction backend, allocator or complete training chain captures successfully.

Use the same product/sum operations for the paired eager and graph timings; retain the original fixed tolerances and all forward/backward matrix products' coverage. A broadcast reduction can use a different addition order from GEMV/GEMM, so numerical agreement must be rechecked. Keep dtype/shape fixed, warm the exact kernels outside capture, retain buffers, and leave host scalar conversion and metric extraction outside capture. A successful test would apply only to this selected path and stack.
